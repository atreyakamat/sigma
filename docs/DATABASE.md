# Database

PostgreSQL 17, accessed from `apps/api` through Prisma 7 with the `@prisma/adapter-pg` driver
adapter. The schema lives in `apps/api/prisma/schema.prisma`; migrations in
`apps/api/prisma/migrations/`. Prisma Client is generated into `apps/api/prisma/generated/`
(gitignored, produced by `prisma generate` on `pnpm install` and before `build`).

**Status:** the schema and the initial migration exist and are applied in CI. No API endpoint reads
or writes any table yet (only `GET /api/v1/health` exists), and the web client stores documents in
the API (ADR-0010). Tables are created by migrations `0001_init` and `0002_auth_rbac` (see the
Milestone 3 section at the end for the additions).

## Conventions

- Model and field names are `camelCase` in Prisma; every model is mapped to a `snake_case` table
  with `@@map` and every multi-word column with `@map` (for example `Document.createdById` →
  `documents.created_by_id`). The API will expose `camelCase` JSON; `snake_case` exists only in
  SQL.
- Primary keys are UUIDs (`@db.Uuid`, generated by Prisma with `@default(uuid())`, not by the
  database).
- Timestamps are `TIMESTAMP(3)`; `createdAt` defaults to `CURRENT_TIMESTAMP`, `updatedAt` is
  maintained by Prisma's `@updatedAt`.
- All foreign keys are `ON UPDATE CASCADE`. `ON DELETE` is `CASCADE` for ownership edges (a parent
  row owns its children), `SET NULL` for optional placement, and `RESTRICT` (Prisma's default)
  for authorship references so a user who created content cannot be deleted while it exists.

## Relationship overview

```
users ─┬─< workspaces (owner)          ─┬─< workspace_members >─ users
       │                                ├─< projects ─┬─< folders (tree)
       │                                │             └─< documents ─┬─< document_snapshots ─< document_versions
       │                                │                            ├─< document_updates
       │                                │                            ├─< comments (tree)
       │                                │                            ├─< document_permissions >─ users
       │                                │                            └─< share_tokens
       │                                └─< assets
       └─ authorship FKs (RESTRICT): projects, documents, assets, comments, document_versions
```

## Document content storage (planned, not used yet)

Document content is **not** stored in a column. The intended layout, for which the tables above
were created:

- **Snapshots in object storage.** A full `DocumentJSON` (the format defined by
  `@sigma/document`, validated and migrated by the same code the client uses) is written to the
  S3-compatible bucket (`S3_BUCKET`, `sigma-assets` in the local MinIO) and referenced by
  `document_snapshots.storage_key`, with `revision`, `schema_version` and `content_hash` for
  integrity and deduplication. Named versions (`document_versions`) point at a snapshot.
- **Update log for realtime sync.** `document_updates` is an append-only log of binary updates
  per document, ordered by `sequence_number`. The planned producer is Yjs (ADR-0004): each
  client update is appended, and the log is periodically folded into a new snapshot so loading a
  document is "latest snapshot + updates since". Until collaboration lands, the log stays empty.

Today the client persists documents through `PUT /documents/:id/content` into `documents.content` (ADR-0010).

## Migration workflow

Prisma is configured in `apps/api/prisma.config.ts`: schema path, migrations path and the
datasource URL from `DATABASE_URL` (falling back to the Docker Compose database so
`prisma generate` works without a `.env`). `apps/api/prisma/migrations/migration_lock.toml` pins
the provider to `postgresql`.

Scripts (run from the repo root):

| Command                                               | What it does                                      |
| ----------------------------------------------------- | ------------------------------------------------- |
| `pnpm --filter @sigma/api prisma:generate`            | regenerate Prisma Client into `prisma/generated/` |
| `pnpm --filter @sigma/api prisma:migrate`             | `prisma migrate deploy`: apply pending migrations |
| `pnpm --filter @sigma/api exec prisma migrate diff …` | produce or check migration SQL (see below)        |

Local setup:

```sh
docker compose -f infrastructure/docker/docker-compose.yml up -d
cp apps/api/.env.example apps/api/.env
pnpm --filter @sigma/api prisma:migrate
```

### Creating a migration

Migrations are plain SQL files produced with `prisma migrate diff`, not `prisma migrate dev`:

1. Edit `apps/api/prisma/schema.prisma`.
2. Generate the SQL delta against a database that has the current migrations applied:

   ```sh
   cd apps/api
   mkdir -p prisma/migrations/0002_<name>
   pnpm exec prisma migrate diff \
     --from-config-datasource \
     --to-schema prisma/schema.prisma \
     --script > prisma/migrations/0002_<name>/migration.sql
   ```

   (The initial migration was produced with `--from-empty` instead of
   `--from-config-datasource`.)

3. Review the SQL, then apply it: `pnpm --filter @sigma/api prisma:migrate`.
4. Regenerate the client: `pnpm --filter @sigma/api prisma:generate`.
5. Keep `infrastructure/database/` in sync: it holds a copy of each migration's SQL
   (`0001_init.sql` is byte-identical to `prisma/migrations/0001_init/migration.sql`) for
   environments that apply SQL without the Prisma CLI.

### CI check

The `api-migrations` job in `.github/workflows/ci.yml` starts `postgres:17-alpine`, runs
`prisma migrate deploy`, then

```sh
prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code
```

which fails when the migrated database and `schema.prisma` differ. A schema change without a
matching migration therefore fails CI.

## Milestone 3 additions (migration `0002_auth_rbac`)

- `users`: `system_role` enum `SystemRole` (`ADMIN` | `MEMBER`, default `MEMBER`), `active`
  boolean (default true), `must_change_password` boolean (default false); `password_hash` is now
  required.
- `sessions`: `id`, `token_hash` (unique, SHA-256 of the cookie token), `user_id` → `users`
  (cascade), `created_at`, `last_seen_at`, `expires_at`; index on `user_id`.
- `documents`: `content` JSONB (latest validated document), `revision` int (default 0, incremented
  on every content save; clients must present it), `node_count` int, `thumbnail` text (data URL).

The SQL is mirrored in `infrastructure/database/0002_auth_rbac.sql`. Migrations are applied by the
API container entrypoint (`prisma migrate deploy`) on every start.
